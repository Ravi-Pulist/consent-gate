Consent as exclusion, not masking

A retrieval system over patient records. The team says it respects consent, because it masks identifiers. Masking answers a different question: it hides who, and consent governs whether. This page is the gap between the two, measured on the same corpus with the same probes under both configurations.

Everything here is synthetic. 200 invented patients, 1,000 generated notes, MRN-ZZ- identifiers, 555-01xx telephone numbers and .invalid email domains, produced by corpus/generate.py from seed 20260804. No real patient data enters this project, and none is needed to show the failure.

The masking baseline is not a straw man. It redacts every direct identifier at 100% recall, which is possible only because the corpus is synthetic and all 5,000 identifier offsets are known (5 per document, across 1,000 documents). Every leak above survives a perfect masker. A real NER masker also misses identifiers outright, so this understates the failure rather than exaggerating it.

The search oracle

A hit, a count, even an empty result set is information about who is in the index. The corpus seeds 30 pairs: one token that appears in exactly one non-consented record, and one token that appears nowhere at all. If the two responses differ in any observable way, the index answers the question "is this person in your data".

Why post-filtering does not work

The tempting implementation is to retrieve normally and drop non-consented records from the results. It leaks on three surfaces at once, and each one is a working oracle.

surfacehow post-filtering leaks
counts"1,204 matches, showing 8". The 1,204 was computed over everyone, including the withdrawn. The number is the disclosure.
scoresranks and any normalisation are computed over the full set, so the shape of the surviving scores shifts with what was removed.
paginationa short page, or offset arithmetic that skips, marks exactly where a record was removed.

src/consent_gate/gate.py module docstring

There is a correctness cost too: top-k-then-filter returns fewer than k, and over-fetching to compensate makes the retrieval budget depend on how many hidden records exist, which is another oracle built to fix the first one. The rule that resolves all of it: exclusion is a property of the candidate set, not of the result set.

tests/test_sabotage.py implements post-filtering deliberately, as a gate that retrieves over everyone and then drops the non-consented hits, and asserts the probe suite catches it. It does. No forbidden document is returned, and the oracle probe still fires, because the response carries a count computed before the drop.

tests/test_sabotage.py, test_post_filtering_instead_of_exclusion_is_caught

The predicate is inside the query plan

Not applied to results afterwards. This is the engine's own plan for the query that ran, which a reader can check rather than take on trust. SqliteIndex.explain() prints it for any query.

Exclusion

SCAN d
SEARCH c USING COVERING INDEX sqlite_autoindex_consented_1 (subject=?)
USE TEMP B-TREE FOR ORDER BY

c is the consented subject set, joined into the scan.

Masking

SCAN d
USE TEMP B-TREE FOR ORDER BY

No consent predicate exists to push down. Everything is scanned, then redacted.

What this does not close

Three limits carried over from the project README, and three things found while building this page. Each names the file that records it.

Carried from the README

  • Timing. Exclusion closes the content channel. Response time is a separate channel and is not claimed closed here. Measuring it is scoped work, not a checkbox.
  • Postgres and pgvector were not run. The adapter interface is the extension point and the reference path is specified, but no Postgres was available in this environment. Every number on this page came from the SQLite path, and the SQLite plan is the one quoted above. Claiming a pgvector result without running it would be the vendor behaviour this project exists to oppose.
  • Corpus totals. If overall corpus size is published, consented-count changes leak consent events by differencing. This gate exposes no totals; a deployment that does reopens the channel.
  • Retrieval quality is not what the exhibit tests. Embeddings are a deterministic hashed bag of words so a sceptic can reproduce the run without downloading a model. Swapping in a real embedding model does not change where the consent predicate is applied, which is the claim.
  • Differential privacy for aggregates is a different tool for a different problem: exclusion fixes membership, DP perturbs values. Compatible, out of scope.

README.md, Not verified. Also exhibits/exhibit.md, What this does not close.

Found while building this page

  • 79 consented and 120 not do not add to 200. The exhibit takes its consented count after the revocation drill has already revoked P001, while the non-consented set was computed before it. At the measured instant the split is 80 and 120. The leak measurements used the pre-drill split, so they are unaffected; the reported count is one low. src/consent_gate/exhibit.py, counts computed after run_drill; src/consent_gate/revocation.py, store.revoke inside the drill. Re-derived by verify.py.
  • The two count-channel leaks are attributed to the wrong cause. The evidence string says the gap is the set filtered out after being counted. In this run the page walk stopped at the probe's 52-page limit: masking reports 847 matches for review and 520 were walked before the cap, against 326 reported and 326 walked under exclusion. The channel is real, since 847 is a total over everyone and 326 is not, but the sentence describing it is wrong. src/consent_gate/probes.py, probe_pagination page cap. Re-derived by verify.py.
  • The aggregates row of the drill is not a membership test. The drill was called without a stratum, so that surface's check returns false without consulting the gate and its 0.0000 s measures nothing. The three other surfaces are real measurements, and the worst-surface figure comes from the search surface, so the headline is unaffected. src/consent_gate/revocation.py, the aggregates measure with stratum unset.

Reproduce it

From the repository root. src/consent_gate imports the standard library only; pytest is needed for the test suite and nothing else is:

export PYTHONPATH=src
python corpus/generate.py
python -m consent_gate.cli exhibit --corpus corpus/data \
    --out exhibits/exhibit.md --json exhibits/exhibit.json
python -m pytest -q
python examples/demo/verify.py

Corpus generation is deterministic and byte-reproducible from seed 20260804; the manifest carries the generator's own SHA-256 (482304f5...). The leak counts, query plans and fingerprints are deterministic too: running all four commands into a scratch copy of this repository reproduced the corpus byte for byte, and the re-run exhibit differed from the published one in three fields, all of them revocation timings. Those are wall-clock measurements and will differ on your machine; everything else on this page will not.

The exhibit exits 0 if exclusion leaked nothing, 1 if it leaked, and 2 if it could not run, including the case where the masking baseline leaked nothing, because that means the corpus has no traps in it and a green run would be green for the wrong reason.

examples/demo/verify.py re-derives every figure on this page from exhibits/exhibit.json, corpus/data/manifest.json, a live replay of the query through both gates, and the test collection, then prints a pass/fail tally. It reports 108 of 108 checks passing on this checkout, and lists the three figures it cannot check.
